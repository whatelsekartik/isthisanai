The parameter counts differ because matching *both* depth and width exactly is impossible for two different architectures at the same block count; the transformer is the larger model by 13.4 %, so any Cadence win is a win net of a parameter handicap, and any loss is not explained away by size.

**Equal-*time* control.** The transformer trains ~5x faster per token on CPU (its work is batched matmul; the delta recurrence is elementwise), so an equal wall-clock run was also trained: 4,500 steps / 13,824,000 tokens in 1071 s reaches val loss 4.0307 (ppl 56.30). That is the comparison that favours the transformer, and it is reported here because the equal-token comparison above flatters Cadence.

## 5. What these numbers do and do not show

* The transformer baseline is trained at the same budget, so the comparison is a like-for-like measurement of *this* corpus at *this* scale, not a claim about the architectures at large scale.
* 4-6 M tokens and 1.5 M parameters is far below the regime where linear-attention family differences are usually resolved; treat the loss comparison as a sanity check that Cadence trains properly, not as a ranking.
* All latency numbers are single-process, single-session, no batching. Batching would favour the transformer relative to these numbers (it has more matmul work per token); concurrency would favour Cadence (its per-request state is 216 KB).
